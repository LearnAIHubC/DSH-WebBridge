# 可行性边界

结论分三层：**技术上能做**、**平台允许才能做**、**合规上你自担**。

---

## 1. 平台矩阵（截至 2026-11，产品能力会变，接入前请自行确认）

| 站点 | 模式 A（DOM 驱动问答） | 模式 B（让网页版调 MCP） | 说明 |
| --- | --- | --- | --- |
| ChatGPT 网页版 | ✅ 可做 | ⚠️ 有条件可做 | 需要支持连接器/开发者模式的账号档位；MCP 端点必须公网 HTTPS 可达；连接器由人添加 |
| DeepSeek 网页版 | ✅ 可做 | ❌ 目前无自定义 MCP 连接器 | 只能走模式 A |
| Gemini 网页版 | ✅ 可做 | ⚠️ 视其扩展/连接器能力 | 需实测 |
| Kimi / 通义 / 豆包等国内网页版 | ✅ 可做 | ❌ 基本无 MCP 连接器 | 只能走模式 A |
| 自建 Web 聊天（Open WebUI 等） | ✅ 可做 | ⚠️ 自建服务通常自带 API，没必要 | 有 API 就直接用 API |

> 模式 A 的通路与站点无关：只要能"填输入框 + 点发送 + 读消息列表"就行。模式 B 才是站点强相关。

---

## 2. 模式 A 的硬限制（不是实现问题，是本质）

1. **没有原生工具调用**。只能提示词约定 + 文本解析，模型偶尔不守格式；必须做纠错与降级（见 PROTOCOL.md）。
2. **没有 system 角色**。你的"系统提示"只能作为用户消息注入，优先级低于站点自己的系统提示；某些站点会拒答或改写。
3. **上下文不可控**。网页版有隐藏的上下文上限和摘要策略，长任务会被悄悄截断；必须主动开新会话。
4. **风控**。高频自动化会被判定异常（验证码、限流、甚至封号）；只能低频、持久 profile、稳定指纹，遇验证就停。
5. **流式完成判定**。回复是渐进渲染的，"发完了"只能靠观测推断（停止按钮消失 + 文本稳定 + 无 mutation），永远有误判概率。
6. **延迟与稳定性**。一轮问答秒级到几十秒，且不可重试加速；不适合放进高频工具链。

**适用**：低频、单会话、人对结果有预期校验的场景——"用网页版模型帮我看看这段代码 / 起草这段文字 / 交叉验证一个结论"。
**不适用**：批量、并发、长上下文、要求确定性输出的流水线。

---

## 3. 模式 B 的前置条件

1. 站点支持自定义 MCP 连接器（目前主要是 ChatGPT 的开发者模式连接器）。
2. 一个**公网可达的 HTTPS 端点**：Cloudflare Tunnel（quick tunnel 即可）或自有反代。
3. 端点鉴权：插件自带 Bearer token，且只暴露白名单工具。
4. 连接器由**人**在网页端添加/授权；插件只能提示，不能代点。

**必须接受的现实**：模式 B 里 ChatGPT 的工具调用是**它服务端直接打你的公网地址**，不经过浏览器。浏览器只负责"发任务、看结果"。所以"通过浏览器发消息让网页版调 MCP"其实是两条独立通道的组合，不是一条。

---

## 4. 安全与合规（必须写清楚）

- **网页内容是不可信输入**：DOM 里的文本、模型输出都可能包含提示词注入。所有工具执行必须经过 DSH 的 allow/deny/ask 策略与人工审批，插件不得自动批准。
- **公网 MCP = 远程执行入口**：默认关闭、默认只读白名单、token 必须随机且可轮换、可一键停用。
- **账号条款自担**：多数网页版 ToS 禁止自动化访问或绕过官方接口。本项目不鼓励、不协助规避风控；你自行承担账号风险。
- **不代替登录/验证**：登录、验证码、滑块永远由人在可见浏览器完成；这是硬规则，写进代码闸门。

---

## 5. "能做"的定义（本项目的验收口径）

- 模式 A：在已登录 profile 上，**一句问答 30 秒内拿到正确回复**，失败时返回可诊断的结构化错误。
- 模式 A+：**3 轮工具调用不出现协议解析错误**，且写操作仍触发 DSH 审批。
- 模式 B：网页版能**列出并成功调用至少 1 个只读工具**，非白名单工具返回 403。

达不到这三条就不算交付，只算原型。
